The Model Is Not the Bottleneck. The Harness Is.

Five findings from A-EVOLVE on when a harness unlocks capability, when an evolution loop learns, and when the available feedback makes learning impossible.

Read the full technical write-up ↗

We ran A-EVOLVE across SkillBench, MCP-Atlas, TerminalBench 2.0, and SWE-Bench Verified expecting to learn how agents improve. The repeated pattern was more specific: frontier models often already had the needed capability. The harness determined whether that capability appeared at the right moment, and the evolution loop determined whether the harness could improve over time.

This note records the five findings I would carry forward when building the next self-evolving agent.

1. Verification was a deployment problem, not a missing capability

Opus 4.6 routinely verifies its own work on short interactive tasks: it writes code, runs tests, inspects output, and fixes failures. On long-horizon TerminalBench 2.0 tasks, the same model often spent its budget executing commands and stopped without checking the result.

Our intervention was deliberately small: a self-verification skill and a one-line system-prompt nudge that made the agent load the skill near the end of the trajectory. On 21 unstable tasks, pass rate increased from 33.33% to 66.67%. Across the full benchmark, the agent reached a 76.5% pass rate, while observed verification frequency rose from 24% to 78%.

The lesson: we did not teach the model how to verify. We changed the harness so that an existing capability was deployed at the right time.

2. The evolver independently discovered that verification mattered

On MCP-Atlas, we started with an empty skill library and 500 multi-step reasoning tasks. Across 17 evolution cycles, the evolver wrote five skills from scratch. Three of the five made verification a core component.

No instruction told the evolver to prioritize verification. The task failures supplied the pressure: the agent would select the wrong entity, fail to check it, and build the rest of the trajectory on that initial error. The model knew how to compare entities and attributes. What it lacked was a harness rule that made the comparison happen.

3. The loop corrected its own bad interventions—twice

At cycle 12, the evolver added a generic completeness-check skill. Performance dropped by roughly 10 percentage points. At cycle 13, it removed the skill and wrote the failure into its own memory: generic checklist-style skills should be avoided.

At cycle 15, it tried a single-fact-lookup skill. Performance dropped by roughly 10 points again. At cycle 16, the evolver removed that skill as well.

These were two complete add → observe → remove → generalize cycles without a human selecting the correction. The useful unit of self-improvement was not “the agent wrote a skill.” It was that the system could form an intervention, observe its effect, reverse it, and retain the lesson.

4. More feedback made the evolver worse

We varied how much information the evolver saw after failed SWE-Bench Verified attempts on 13 hard tasks:

  • Trajectory only, no score: 4/13 (30.8%).
  • Score, failure type, and edited files: 8/13 (61.5%).
  • Add failing test names: 4/13 (30.8%).
  • Add full patch diffs: 2/13 (15.4%).

Too little feedback prevented the evolver from localizing the failure. Too much anchored it to the failed implementation: instead of extracting a reusable pattern, it began repairing the previous patch and overfitting to one attempt. The middle level preserved the failure signal while abstracting away the implementation that produced it.

The lesson: more feedback is not better feedback. An evolution loop needs the level of detail that exposes the causal lesson without anchoring it to a failed trajectory.

5. A loop cannot learn constraints its feedback never exposes

The harder limit appeared on a manufacturing scheduling task. A human-curated skill succeeded where the evolved skill failed because it contained one verifier-specific constraint: never start an operation earlier than the baseline.

That rule was not available in the task description or ordinary failure trace. It depended on knowledge of how correctness was judged. Scores and trajectories could not identify a constraint that never became legible in either signal.

This is a general boundary for autonomous evolution. The loop can only learn from what the environment makes observable. Verifier logic, environment-specific constraints, or external domain knowledge require either better instrumentation or a way for the agent to acquire evidence beyond its existing trajectory.

What I take from these results

The harness is not merely scaffolding around the model. It is a design object that determines when capability appears, what failures become visible, and which lessons an evolution loop is able to retain.

A capable model plus a weak harness can look incapable. A strong evolution algorithm plus the wrong feedback can learn the wrong lesson. Self-improving agents need both: a harness that makes capability deployable and a loop that makes the consequences of each intervention legible.
